# Coverage formats: per-function coverage for Python, Rust and C++

Status: research complete (2026-10-26). Resolves `.scratch/slopmeter-phase1/issues/02-coverage-formats.md`.

## Answer

No tool's `FN`/`FNDA` records give slopmeter what CRAP needs directly, so per-function coverage must be derived from `DA` line records intersected with slopmeter's own function line ranges. CRAP wants a *fraction* of the function covered (crap4j uses JaCoCo's per-method instruction counters); `FNDA` only says whether or how often a function was *entered*. coverage.py writes `FN:<start>,<end>,<dotted name>` and `FNDA:<0|1>,<name>` (hit is boolean, and itself derived from `DA`). cargo-llvm-cov and clang both go through LLVM's `llvm-cov export -format=lcov`, which writes `FN:<start>,<raw mangled name>` with no end line, ignores `-Xdemangler`, emits one record per generic/template instantiation at the same line and a separate record per closure/lambda; `FNDA` is a true entry count. gcc's gcov via `geninfo` writes start and end lines (gcc 9+), mangled names unless `--demangle-cpp`, and folds same-line instantiations into one function; `FNDA` is an entry count; lcov 2.2+ writes `FNL:`/`FNA:` instead of `FN:`/`FNDA:`. The names are therefore three incompatible schemes, and only the gcov path carries an end line. `DA` records are present and unambiguous in all three, so the robust design is: parse `DA` per file, map each executable line to the enclosing function from slopmeter's own parser, and compute `covered / executable` per function, optionally using `FNDA` as a cross-check or zero-hit fast path.

## The LCOV tracefile format (lcov's own reference)

The authoritative description is the `TRACEFILE FORMAT` section of the `geninfo` man page in the lcov repository. Relevant facts:

- A section is `TN:`? `SF:` ... `end_of_record`; coverpoint records inside it may appear in any order. Summary pairs are mandatory beside their coverpoints: `LF:`/`LH:` with `DA:`, `FNF:`/`FNH:` with `FN:`/`FNDA:`/`FNL:`/`FNA:`, `BRF:`/`BRH:` with `BRDA:`.
- Legacy function records (what coverage.py and llvm-cov emit) are `FN:<line number of function start>,[<line number of function end>,]<function name>` and `FNDA:<execution count>,<function name>`. The man page says the end line "is optional, and is generated only if the compiler/toolchain version is recent enough (e.g. gcc 9 or newer)".
- "The format of the function coverage data has changed from LCOV 2.2 onward. The tool continues to be able to read the old format but now writes only the new format": a leader `FNL:<index>[flags],<start>[,<end>]` followed by one `FNA:<index>[flags],<count>,<name>` per *alias*. "A function has at least one alias - its own name - and C++ templates, clones and Java lambdas add the rest" (`lcovutil.pm`, package `FunctionAlias`). `FNF:`/`FNH:` count function groups, not aliases. The writer in `lcovutil.pm` (around line 18918) prints only `FNL:`/`FNA:`; current tags are v2.3 through v2.6.
- `DA:<line>,<count>[,<checksum>]`; the checksum is an MD5 of the source line, base64 without padding.

Slopmeter's parser must accept both the legacy and the 2.2+ function records, and must not assume `FN` has an end line or a unique name.

## Python: `coverage lcov`

Source: `coverage/lcovreport.py` and `coverage/regions.py` on the `main` branch of nedbat/coveragepy; command added in 6.3, function records added by PR #1851 ("function coverage!"), released in 7.6.2 (2024-10-09) per `CHANGES.rst`.

**Records emitted.** Per file: `SF:`, `DA:` for every statement (`hit = int(line not in analysis.missing)`, so `DA` counts are 0/1, never execution counts; the source comment says "Q: can we get info about the number of times a statement is executed?"), `LF:`/`LH:` when there are statements, then the function block, then `BRDA:`/`BRF:`/`BRH:` only when branch data exists, then `end_of_record`. `lcov_functions` deliberately writes the legacy format: "lcov 2.2 introduces a new format for function coverage records. We continue to generate the old format because we don't know what version of the lcov tools will be used to read this report."

**FN content.** `FN:{first_line},{last_line},{name}` then `FNDA:{hit},{name}`, where `first_line = min(region.start, min(region.lines))` (the `def` line) and `last_line = max(region.start, max(region.lines))` (last line of the body, including blank/comment lines). `hit = int(analysis.numbers.n_executed > 0)` with the comment "A function counts as having been executed if any of it has been executed." So `FNDA` is boolean and is computed from the same line data as `DA`. Functions with zero statements are skipped and not counted in `FNF`. The `[lcov]` config section only controls output path and line checksums (`line_checksums`, default false).

**Naming.** `regions.py` walks the AST and names each region with `fq_node_name()`, i.e. the dotted chain of enclosing class and function names: `func1`, `MyClass.method`, `outer.inner`, `Outer.Inner.method`. Only `ast.FunctionDef`/`AsyncFunctionDef` produce function regions; lambdas and comprehensions are not regions, so their lines stay in the enclosing function. Nested function bodies are subtracted from the enclosing function's line set ("Function bodies should be excluded from the nearest enclosing function"), and lines in methods belong to both the method region and the class region. Since 7.17.0 (2026-10-22) duplicate names (property getter/setter, conditionally defined functions) get an `@<line>` suffix because "recent versions of the lcov tool complain if the same function name appears more than once"; earlier versions emit the duplicate verbatim. Control characters in names are replaced by `?` (`lcov_field`).

**Verdict.** `FN` is reliable for start/end and gives a stable dotted name, but `FNDA` is a boolean derived from `DA`. Per-function fractions must come from `DA` ∩ line range. coverage.py's regions can serve as a cross-check of slopmeter's own ranges, and its nested-function exclusion is a sensible convention for slopmeter to copy.

## Rust: `cargo llvm-cov --lcov`

Sources: cargo-llvm-cov README and `src/report.rs`, `src/demangler.rs`; LLVM `llvm/tools/llvm-cov/CoverageExporterLcov.cpp`, `CodeCoverage.cpp`, `lib/ProfileData/Coverage/CoverageMapping.{h,cpp}`; rustc's `instrument-coverage.md`; rustc's `tests/coverage/*.cov-map` expectations; cargo-llvm-cov issues #325 and #382.

**Pipeline.** `--lcov` "internally calls `llvm-cov export -format=lcov`" (README; `report.rs` `llvm_cov_args`). The README's `--skip-functions` maps to llvm-cov's `-skip-functions` ("Skip exporting per-function coverage data"). `-C instrument-coverage` "automatically enables `-C symbol-mangling-version=v0`" and by default "instruments all functions, including unused functions and unused generics" (rustc docs).

**Records emitted (from the exporter source).** The header comment of `CoverageExporterLcov.cpp` and `renderFile` give the layout: `SF:`, then for each function `FN:<start>,<name>`, then for each function `FNDA:<count>,<name>`, `FNF:`/`FNH:`, `DA:<line>,<count>` for each instrumented line, `BRDA:`/`BRF:`/`BRH:` (branches are off unless enabled), `LF:`/`LH:`, `end_of_record`. `renderFunctions` writes `F.CountedRegions.front().LineStart` and the raw `F.Name`; there is no end line. Functions are selected with `getCoveredFunctions(Filename)`, which keeps records whose `Filenames[0]` is the section's file, so a function appears under the file that holds its body.

**Names are mangled, even with a demangler.** `FunctionRecord::Name` is documented as "Raw function name". `-Xdemangler` is handled in `CodeCoverage.cpp::demangleSymbols`, which only fills a `DemangleCache` used by `show`/`report`; neither `CoverageExporterLcov.cpp` nor `CoverageExporterJson.cpp` references the cache. cargo-llvm-cov passes `-Xdemangler=<itself>` only for `show` (text/HTML), and its maintainer states in issue #325: "`llvm-cov export` seems to ignore the -Xdemangler flag ... this does not seem to be an issue that can be addressed on cargo-llvm-cov side." Issue #382 shows real `--lcov` output: `FN:238,_RNCNCNCNvNtCsgkPIuEin8tU_24peregrinator_xapp_runner6runner3run0s_00Csh...`. The FN name field in Rust LCOV output is therefore a v0-mangled symbol; slopmeter would need `rustc-demangle` to read it. I confirmed the same behaviour empirically with Apple clang's `llvm-cov` 21 (same exporter): `export -format=lcov -Xdemangler=c++filt` still printed `_Z5twiceIiET_S0_`, while `report -Xdemangler=c++filt` demangled.

**Duplicates.** Issue #325 documents the same function appearing twice with different crate disambiguators in the mangled name when several test binaries include the crate, each with its own `FNDA` count. Demangling collapses the names but not the records, so a consumer keyed on name must merge counts.

**Generics and closures.** `CoverageMapping.h` says "it's possible for a function to have more than one instantiation (consider C++ template specializations or static inline functions)" and groups them in `InstantiationGroup`s; `loadFunctionRecord` dedupes only identical `(filenames, name)` pairs. Each monomorphization is a distinct mangled name, so the LCOV output holds several `FN`/`FNDA` records at one start line (my clang run: `FN:3,_Z5twiceIdET_S0_` and `FN:3,_Z5twiceIiET_S0_`, with `FNF:2` counting two *functions* for three `FN` lines, and `DA:3,2` holding the combined count). rustc's docs: "A function is considered to be executed if any of its instantiations are executed." Closures are separate function records: rustc's `closure_bug.cov-map` lists `closure_bug::main` and `closure_bug::main::{closure#0}` … `{closure#3}`; `closure_unit_return.cov-map` shows closures flagged `(unused)` when never called. The closure's first mapping starts at the line of its body expression (line 14 in that test), not at `let a =` (line 10), so the closure's `FN` line is inside the enclosing function's range. The enclosing `fn`'s first mapping starts on the `fn` line (line 7, col 1).

**JSON alternative.** `cargo llvm-cov --json` is `llvm-cov export -format=text`; per the exporter header it carries a `functions` array with `name`, `count`, `regions` (each `[startLine, startCol, endLine, endCol, count, fileID, expandedFileID, kind]`) and `filenames`. This gives end positions and per-region counts that LCOV lacks, but names are still mangled (confirmed in my run: `main.cpp:_ZL10file_locali`).

**Verdict.** `FN` is usable only as "a function record starts here"; the name is mangled, there is no end line, instantiations and closures multiply records, and duplicates across binaries occur. `FNDA` is a real entry count but not a coverage fraction. Derive per-function coverage from `DA` ∩ slopmeter's ranges; treat closures as part of the enclosing function (or as their own units) by slopmeter's own policy.

## C++: gcc/gcov via `lcov --capture`, and clang via llvm-cov

### gcc + gcov + geninfo

Sources: GCC manual "Invoking Gcov" and "Gcov and Optimization"; lcov `geninfo` man page, `lcovrc` man page, `bin/geninfo`, `lib/lcovutil.pm`.

**Input.** `geninfo` "internally uses gcov to extract coverage data from .gcda and .gcno files using the best supported gcov file format"; for gcc 9+ that is `--json-format`. The GCC manual documents each JSON function as `{blocks, blocks_executed, demangled_name, end_column, end_line, execution_count, name, start_column, start_line}` with the caveat "start_line and start_column do not include any template parameters and the leading return type". Each line object may carry `function_name` ("for a line with an inlined statements can be not set"). gcov's own `-m/--demangled-names` option exists, but geninfo reads the JSON and chooses the field itself.

**FN emission (from `bin/geninfo`).** Around line 3806: `$name = $lcovutil::demangle_cpp_cmd ? $d->{demangled_name} : $d->{"name"}` then `define_function($name, $start_line, $end_line)`. So without `--demangle-cpp` the name is the Itanium-mangled symbol; with it, gcov's demangled name (lcov also accepts an external filter such as `c++filt`, default when the option is given with no argument). The man page: "--demangle-cpp: Demangle C++ method and function names in captured output", and `lcovrc` notes "This option is not required if you are using gcc/9 or newer; these versions report function begin/end lines directly."

**Same-line aliasing.** `lcovutil.pm::define_function` looks up by name, then by start line (`findKey($start_line)`); a different name at an existing start line becomes an alias of that function (`addAlias`), with an `inconsistent` error if end lines disagree ("pick the highest end line"). Hence template instantiations, compiler clones (`.constprop`, `.isra`) and the lambda `operator()` on a declaration line collapse to one function entry with several aliases: in lcov ≥ 2.2 one `FNL:` plus one `FNA:` per alias; `FNF`/`FNH` count groups. The `lcovrc` `collapse_callgraph_alias` text confirms "Each instantiation of a template, and each clone the compiler makes of a function, is an alias of one function."

**Inline functions in headers.** gcov attributes a function to the file containing its definition, so header functions appear in the header's `SF:` section. GCC warns that "Inlineable functions can create unexpected line counts": out-of-line copies may be emitted in several objects and "all but one use of that function will show zero counts", and when inlined in several places "the line counts themselves might seem inconsistent". Compile with `-O0` for sane per-function data. Lambdas are detected by name ("demangled name contains `{lambda(` or whose mangled name contains a closure type (`Ul...E_`)") only for consistency checks; they still get their own function record at the lambda's line, inside the enclosing function's range.

**Verdict.** This is the best FN data of the three: start *and* end line (gcc 9+), readable names with `--demangle-cpp`, and a true entry count. But `FNDA`/`FNA` is still an entry count, not a fraction; the record shape depends on lcov version (`FN`/`FNDA` vs `FNL`/`FNA`); and names depend on the `--demangle-cpp` flag the user happened to pass. Derive fractions from `DA` ∩ ranges; optionally use `FN`/`FNL` start/end to validate slopmeter's ranges.

### clang + llvm-cov

`llvm-cov export -format=lcov` on clang-instrumented binaries is the Rust pipeline above, minus cargo. clang's docs: "Template functions and static inline functions from headers are two kinds of functions which may have multiple instantiations." My run on a two-TU sample confirmed: header functions appear under the header's `SF:`; `FN:3,_Z5twiceIdET_S0_` and `FN:3,_Z5twiceIiET_S0_` at one line; a lambda as `FN:6,main.cpp:_ZZ11with_lambdaiENK3$_0clEii` and a `static` function as `FN:3,main.cpp:_ZL10file_locali` (internal-linkage names are prefixed with the defining file and a colon, and may contain `$`); `FNDA` carries real counts (`FNDA:2,_Z13header_inlinei`); never-called functions are present with `FNDA:0`; no end line; `-Xdemangler` ignored. lcov's `--demangle-cpp` can post-process these names if the user runs the file through `lcov`, but slopmeter should not assume that. lcov also ships `llvm2lcov` for the JSON export.

## Implications for slopmeter

1. Build one LCOV reader that keeps, per `SF:`, the `DA` map (line → count) and tolerates `FN`/`FNDA`, `FNL`/`FNA`/`FNM`, `BRDA`, `MCDC`, `VER`, `TN`, comments and blank lines. Treat `DA` counts as the only cross-tool truth; treat coverage.py's counts as booleans.
2. Compute coverage per function as `|{l ∈ range : DA[l] > 0}| / |{l ∈ range : DA[l] exists}|` using slopmeter's own parser ranges; lines without a `DA` record are non-executable and ignored. Decide explicitly whether nested functions/closures/lambdas are subtracted from the parent (coverage.py does; LLVM and gcov report them separately but their lines also carry `DA` records inside the parent's span).
3. Use `FNDA`/`FNA` only as optional corroboration: if any `FN` whose start line falls in the range has a non-zero count but the derived fraction is 0, the ranges are probably misaligned (gcov's `start_line` excludes template heads and return types; coverage.py's start is the `def` line; LLVM's is the first counted region).
4. Do not key anything on `FN` names: three schemes, mangled by default on two of them, duplicated across instantiations and binaries, and name-suffixed in newer coverage.py.
